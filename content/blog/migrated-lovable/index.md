> 원문: [How we migrated lovable.dev away from Next.js and turned it into another Lovable app](https://lovable.dev/blog/how-we-migrated-lovable-dev-away-from-nextjs)

[lovable.dev](https://lovable.dev)는 방문자가 상당히 많은 웹사이트입니다. 월간 순 방문자 수가 4,200만 명이 넘습니다. 구조도 꽤 복잡합니다. 라우트가 거의 400개이고, 생성된 코드를 제외해도 코드가 91만 줄을 넘습니다. 에이전트 도구를 150개 이상 지원하며, 구문 강조 기능을 갖춘 작은 IDE까지 들어 있습니다. 이제 이 사이트도 다른 Lovable 앱과 마찬가지로 Lovable에서 호스팅합니다.

## 이 작업을 한 이유

마이그레이션 전 lovable.dev는 Vercel에서 호스팅하는 Next.js 앱이었습니다. 처음에는 다른 곳에서 호스팅했지만 규모가 커지면서 로컬과 프로덕션 간 빌드 호환성이나 특정 지역의 느린 로딩 시간 같은 문제를 겪기 시작했습니다. Vercel은 훌륭하게 제 역할을 했고, 옮긴 뒤에는 문제가 사라졌습니다. 그런데도 몇 가지 이유로 호스팅을 Lovable로 옮기기로 했습니다.

자사 제품을 사용하는 가장 큰 이유는 개밥먹기입니다. 사용자가 겪는 어려움을 직접 체감하고, 피드백 주기를 최대한 짧게 만들어 사용자에게 더 나은 제품을 제공하고 싶습니다.

단일 앱 확장의 한계에도 도전하고 싶습니다. 지금까지는 수천만 개의 앱을 호스팅하는 데 능숙했습니다. 일반적인 앱은 규모가 작고 트래픽도 적습니다. 하나의 앱에서 수천만 명의 방문자를 지원하는 일은 그 자체로 새로운 과제가 있는 다른 문제입니다. 우리 서비스를 위해 개선한 내용은 Lovable에서 앱을 운영하는 모든 빌더에게도 자동으로 도움이 됩니다.

마지막으로, 최고의 웹 앱을 만드는 데 필요한 내부 지식을 빌더 에이전트에 다시 반영하고 모든 사용자가 자기 앱에서 그 혜택을 누리게 하고 싶었습니다. 기술 스택을 통일하면 어느 때보다 수월하게 할 수 있습니다.

## 앱 호스팅 방식의 배경

현재 Lovable은 주로 TanStack Start 앱을 만들고 호스팅합니다. 이 프레임워크는 동형 실행(isomorphic execution), 간편한 배포, 타입 안정성이라는 요구에 특히 잘 맞습니다. 이 프레임워크를 선택한 이유와 활용 방식은 [“TanStack Start로 앱 만들기”](https://lovable.dev/blog/building-apps-using-tanstack-start) 글에서 더 자세히 볼 수 있습니다. 게시된 Lovable 앱은 각각 Cloudflare의 `workerd` 런타임용 워커로 빌드합니다. 그런 다음 하나의 진입 워커가 각 앱의 코드를 불러와 [워커를 동적으로 생성](https://developers.cloudflare.com/dynamic-workers/)하고 요청을 전달하면서 모든 앱을 서비스합니다.

각 동적 워커는 자체 V8 아이솔레이트(isolate) 샌드박스에서 실행됩니다. 아이솔레이트는 제어 프로세스 안에 있는 독립적인 V8 힙으로, 별도 프로세스를 쓰는 것보다 비용이 적게 듭니다. 컨테이너와 가상 머신의 차이를 생각하면 됩니다. 아이솔레이트를 인스턴스화하는 데 드는 비용은 워커 번들 크기에 비례합니다. 작은 번들이면 4ms 정도지만, 매우 큰 번들이면 최대 1초까지 걸릴 수 있습니다. 아이솔레이트를 캐시에 저장해 재사용하므로 여러 요청에 걸쳐 코드 로딩과 인스턴스화 비용을 분산할 수 있습니다. 이 방식 덕분에 수백만 개의 앱을 경제적으로 운영할 수 있습니다. 아이솔레이트는 보통 LRU 방식으로 제거되거나 메모리 한도를 넘었을 때 제거됩니다. 제거가 항상 순조롭게 끝나는 것은 아닙니다. 이 문제는 뒤에서 다시 다루겠습니다.

lovable.dev도 같은 방식으로 서비스하도록 TanStack Start로 마이그레이션했습니다. 이제 lovable.dev는 사용자 앱 6,000만 개 이상 가운데 가능한 목적지 하나일 뿐입니다. lovable.dev를 서비스하는 경로에만 필요한 코드는 200줄도 되지 않습니다. 주로 다른 릴리스 메타데이터 형식과 별도의 옵저버빌리티 설정을 처리합니다.

![호스트 이름 확인, 공통 인프라와 접근 검사를 처리하고 여러 앱 워커 번들 중 하나로 요청을 전달하는 단일 앱 로더 워커. 그중 하나가 lovable.dev 번들입니다.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/app-loader-worker.svg)

*lovable.dev는 다른 Lovable 앱과 동일한 앱 로더 워커가 서비스합니다. 6,000만 개가 넘는 앱 번들 중 하나일 뿐입니다.*

## 마이그레이션 전략

빠르게 개발되는 앱을 마이그레이션하는 일은 결승선이 계속 멀어지는 경주와 같습니다. 처음에는 개발자 한 명이 코드 35만 줄을 바라보며 시작했습니다. 6개월 뒤 마이그레이션을 마쳤을 때 코드는 85만 줄이 넘었고, 그 뒤로도 6만 줄이 더 추가됐습니다. 이곳 사람들은 새로운 기능을 계속 출시합니다.

![2026년 3월부터 7월까지 주 단위 마이그레이션 진행 상황. 마이그레이션한 코드 줄 수는 거의 0에서 85만 줄로 늘고, 미마이그레이션 코드 줄 수는 37만 5천 줄에서 0으로 줄어들며, 진행률은 100%에 도달합니다.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/migration-progress-static.svg)

*주별 마이그레이션 진행 상황입니다. 마이그레이션 내내 전체 코드 규모가 계속 커졌습니다.*

전체 계획은 Lovable에 합류하기 전 제가 크게 후회했던 경험에서 출발했습니다. 기존 시스템을 계속 운영하면서 대규모 일괄 마이그레이션을 병행하고, 기능이 동등해진 뒤 한 번에 전환했던 경험입니다. 이번에는 다르게 하기로 했습니다. 두 프레임워크에서 모든 기능을 계속 작동시키면서 점진적으로 다시 작성했습니다. 돌이켜보면 이 결정이 마이그레이션에서 가장 중요했습니다.

### 두 프레임워크를 함께 운영하기

두 프레임워크를 동시에 실행하고 요청을 알맞은 쪽으로 전달해야 했습니다. 그래야 모든 것을 한 번에 옮기는 대신 라우트별로 마이그레이션할 수 있습니다.

![웹 프록시 워커가 A/B 단계적 배포와 미리 보기 보호를 포함해 프레임워크별 라우팅을 처리하고, 마이그레이션된 라우트는 앱 워커 번들로, 기존 라우트는 Vercel의 Next.js로 전달합니다.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/proxy-routing.svg)

*두 프레임워크 앞에 둔 프록시 워커가 라우트와 사용자별로 요청을 처리할 프레임워크를 결정합니다.*

이 구조에서 중요한 요소 하나는 사용자 경험입니다. 프레임워크 사이를 이동하면 하드 내비게이션이 발생합니다. 브라우저가 새 문서와 새 리소스 묶음을 불러와야 합니다. 반면 프레임워크 내부의 소프트 내비게이션은 새 라우트에 필요한 스크립트와 데이터만 불러오고 나머지는 재사용합니다. 실제로 하드 내비게이션은 훨씬 느립니다. 마이그레이션 전 실제 사용자 기준 중앙값은 약 1.5초였지만, 하드 내비게이션은 약 5초였습니다. 따라서 이런 이동은 가능한 한 드물게 발생하도록 해야 했습니다.

![각 프레임워크 안에서 발생하는 느린 첫 내비게이션과 빠른 내부 내비게이션, 그리고 Next.js와 TanStack Start 사이에서 발생하는 느린 하드 내비게이션을 비교한 다이어그램.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/hard-vs-soft-navigation.svg)

*프레임워크 내부 내비게이션은 비용이 낮습니다. 프레임워크 사이를 이동하면 문서 전체를 새로 불러와야 합니다.*

이를 위해 모든 라우트를 일반적인 사용자 여정에 맞춰 살펴보고 마이그레이션 그룹을 만들었습니다. 사용자가 자주 오가는 라우트는 함께 마이그레이션했습니다. 주요 그룹 다섯 개와 몇 개의 작은 그룹이 생겼습니다. 각 그룹의 단계적 배포는 기능 플래그로 제어해 그룹 안의 전환을 점진적으로 진행했습니다. 배포 과정에서 설정한 비율의 방문자가 두 프레임워크 중 하나에 무작위로 배정됐습니다.

#### 하드 내비게이션을 부드럽게 만들기

하드 내비게이션의 시각적 경험을 개선하는 간단한 방법 하나는 브라우저의 문서 간 [View Transitions API](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@view-transition#navigation)를 사용하는 것입니다. CSS at-rule 하나로 부드러운 교차 페이드 전환을 적용해 기본 동작인 흰 화면 깜박임을 대체할 수 있습니다.

```css
@view-transition { navigation: auto; }
```

전환은 이동 전 페이지와 이동 후 페이지가 모두 이 규칙을 포함할 때만 실행됩니다. 이 규칙을 추가한 뒤 동료들은 하드 내비게이션의 시간이 더 길다는 점 외에는 거의 알아차리지 못했습니다.

#### 프레임워크 고정

이 과정에서 해결한 흥미로운 문제 하나는 사용자가 처음 도착한 앱에 계속 머물게 하는 일이었습니다. 사용자 A가 프로젝트 설정의 Next.js 버전에 배정되면 설정 그룹의 모든 라우트에서도 Next.js를 계속 사용해야 합니다. TanStack Start 버전으로 이동한 사용자 B도 마찬가지로 그룹 안에서 같은 프레임워크를 사용해야 합니다. 이를 위해 라우트 레지스트리와 기능 플래그 메타데이터를 추출하고, 이를 프록시와 두 프레임워크가 함께 사용하는 단일 기준으로 삼았습니다.

래퍼를 적용한 라우터 컴포넌트를 통해 각 프레임워크는 어떤 라우트에서 소프트 내비게이션을, 어떤 라우트에서 하드 내비게이션을 사용해야 하는지 알 수 있었습니다.

#### 결정론적 기능 플래그

무작위 기능 플래그가 적용된 환경에서 종단 간 테스트를 하려면 어떻게 해야 할까요? 두 프레임워크를 모두 안정적으로 테스트하고 예상대로 동작하는지 확인할 수 있도록 프레임워크 선택을 결정론적으로 재정의하는 방법을 만들었습니다. 프록시 서버는 내부 검색 파라미터를 확인해 무작위 값 대신 그 안에 지정된 기능 플래그를 할당합니다.

기능 플래그를 사용하는 모든 시스템에 유용한 기능입니다. 테스트는 결정론적이어야 하고, 현재 진행 중인 무작위 단계적 배포의 영향을 받지 않아야 합니다.

### 코드 공유하기

다음 목표는 Next.js와 TanStack Start 사이에서 코드를 공유하는 방법을 만드는 것이었습니다. 프레임워크별 코드는 5~10%로, 프레임워크와 무관하게 공유하는 코드는 90~95%로 구성하는 게 목표였습니다. 결국 목표에 도달했습니다. Next.js 코드를 제거하기 직전에는 웹 코드베이스에서 Next.js 전용 코드가 3%뿐이었습니다.

![TanStack Start와 Next.js를 표시한 작은 상자 두 개 위에 “이 레이어는 가능한 한 작게 유지”라는 문구가 있고, 그 아래에는 “거의 모든 코드를 여기에”라는 문구와 함께 프레임워크에 종속되지 않는 공통 코드가 큰 상자로 놓여 있습니다.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/shared-code-layers.svg)

*목표 구조는 큰 프레임워크 비종속 코어 위에 얇은 프레임워크 레이어를 두는 것입니다.*

공유 코드 전용 루트 폴더를 만들고 두 프레임워크의 모듈 해석에 `#shared/` 별칭을 연결했습니다. `package.json`의 `imports`에 설정하고 타입 검사기를 위해 `tsconfig.json`의 경로에도 같은 내용을 반영했습니다. 공유 코드가 어느 프레임워크도 가져오지 못하도록 린트 규칙도 추가했습니다.

```json
// web/package.json (TanStack Start)
"imports": { "#shared/*": "./shared/*" }

// app/package.json (Next.js)
"imports": { "#shared/*": "../web/shared/*" }
```

```ts
// works identically in either framework
import { buildUrlPath } from "#shared/lib/routes";
```

```ts
// oxlint.config.ts—shared code stays framework-agnostic, enforced
{
  files: ["web/shared/**/*.{ts,tsx}"],
  rules: {
    "no-restricted-imports": ["error", {
      paths: [
        { name: "next", message: "Shared code cannot depend on Next.js." },
        { name: "@tanstack/react-start", message: "Shared code cannot depend on TanStack Start." },
        { name: "@tanstack/react-router", message: "Shared code cannot depend on TanStack Router." },
      ],
      patterns: [
        { group: ["next/*"], message: "Shared code cannot depend on Next.js." },
        { group: ["node:*"], message: "Shared code cannot use Node.js APIs. Must be runtime-agnostic." },
      ],
    }],
  },
}
```

이 전체 구조를 `AGENTS.md`에 설명하고 몇 차례 다듬자 새로운 기능을 기본적으로 이식 가능한 방식으로 작성할 수 있었습니다.

#### 회귀 방지

마이그레이션 중간쯤에 `#shared` 바깥에서는 새 기능 코드를 작성하지 못하게 하는 검사도 추가했습니다. ‘기능 코드’는 모호한 개념이지만, 에이전트 자동화를 사용하면 결정론적 검사 없이도 검증할 수 있었습니다. 이 검사는 이식 불가능한 코드가 새로 생기는 것을 막았을 뿐 아니라 마이그레이션을 몰랐던 개발자에게도 그 사실을 알려줬습니다. 다음은 검사에서 PR 규칙 준수 여부를 확인한 예입니다.

![PR 자동 검사 결과. 상태는 정상이고, 기능 코드가 있으며, 정책을 준수합니다. 새 기능 로직은 web/shared/lib/favicon에 올바르게 배치됐고 app/의 변경은 프레임워크에 종속된 계측 클라이언트의 두 줄짜리 연결 코드뿐입니다.](https://assets.lovable.dev/content/news/nextjs-migration/portability-check.png)

*이식성 검사는 파일별로 판정 이유를 설명해 작성자가 필요한 순간에 규칙을 배울 수 있게 합니다.*

### 어댑터와 호환성 레이어

공유 코드가 생긴 뒤에도 깊숙이 중첩된 컴포넌트가 내비게이션 버튼을 표시하려고 `next/link`를 가져와야 한다면 어떻게 해야 할까요? 그런 컴포넌트를 프레임워크 전용 코드에 두고 싶지는 않았습니다. 최상위 Provider를 통한 의존성 주입도 잠깐 고려했지만, 그러려면 가져오기를 컨텍스트에서 값을 읽는 방식으로 바꿔야 했습니다. 큰 변경이 될 뿐 아니라 주의하지 않으면 런타임 오버헤드도 생길 수 있었습니다.

결국 인터페이스 기반의 의존성 주입과 비슷한 방식을 구현했습니다. 공유 코드에서 공통 분모가 되는 인터페이스를 선언하고 각 프레임워크가 이를 구현합니다. 그런 다음 타입스크립트 가져오기 별칭을 활용하면 의존성 주입 메커니즘과 직접 상호작용하지 않고도 필요한 항목을 가져올 수 있습니다.

```ts
// app/tsconfig.json:  "@platform/router": ["./lib/router/next-adapter.ts"]
// web/tsconfig.json:  "@platform/router": ["./lib/router/tanstack-adapter.ts"]

// next-adapter.ts
export { usePathname } from "next/navigation";

// tanstack-adapter.ts
export function usePathname(): string {
  return useLocation({ select: (loc) => loc.pathname });
}

// shared code, works under either framework
import { usePathname } from "@platform/router";
```

플랫폼 어댑터를 마련하면서 코드의 90% 이상을 공유 영역으로 옮기는 데 필요한 마지막 조각을 채울 수 있었습니다.

### 핵심만 남기기

프레임워크에 종속된 부분을 줄이는 한 가지 방법은 애초에 프레임워크 API를 적게 사용하는 것입니다. 결국 다른 것으로 대체해야 할 API라면 일찍 시작해 프레임워크 전용 API 일부를 프레임워크와 무관한 것으로 바꾸면 어떨까요? 우리에게는 `next/font`와 `next/image`, 그리고 Next.js에 의존하는 서드파티 라이브러리로 구축한 인증 및 국제화(i18n) 솔루션이 그 대상이었습니다.

Next.js를 계속 운영하는 동안 이런 요소를 먼저 마이그레이션하니 전체 위험이 줄었고 빠르게 얻은 성과도 있었습니다. 예를 들어 새 사내 인증 라이브러리는 안정성을 높이고 Firebase Auth 호출 수를 10배 넘게 줄였습니다. 새 국제화 솔루션은 런타임 성능도 개선했습니다. 페이지 로드 시 국제화 초기화에 드는 CPU 비용이 약 3분의 1로 줄었습니다. 빌드 타임 안전성도 높아져 번역 키의 철자를 틀리면 타입 검사 오류가 발생했습니다.

프레임워크에 대한 의존 범위가 줄어든 뒤에야 본격적으로 마이그레이션을 시작할 수 있었습니다.

![세 단계의 다이어그램. 처음에는 core, next/router, next/fonts, next/image와 서드파티 라이브러리가 Next.js 상자에 들어 있습니다. 다음 단계에서는 상자에 core와 next/router만 남고 이식 가능한 대체 요소가 옆에 추가됩니다. 마지막에는 Next.js와 TanStack Start가 같은 이식 가능한 대체 요소 위에 나란히 놓입니다.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/trimming-framework-surface.svg)

*프레임워크 API를 먼저 이식 가능한 대체 요소로 바꾸면서 마이그레이션해야 할 범위를 줄였습니다.*

## AI를 활용한 코드 이전

마이그레이션 계획을 세울 때 처음에는 “도구를 모두 만든 뒤 제품 기능을 소유하고 유지 관리하는 팀에 작업 대부분을 나눠주자”고 생각했습니다. 이 계획은 현실과 부딪히며 사라졌습니다. 좋은 방향으로 말입니다. 처음에는 “에이전트가 PR 초안을 만들고 담당자가 검토하고 테스트한다”로 바뀌었습니다. 그러다 초안의 품질이 충분히 좋아져 제가 직접 묶음 단위로 검토하고 반영하게 됐습니다. 결국 어떤 팀도 마이그레이션 몫을 배정받지 않았습니다.

마이그레이션을 진행하면서 몇 가지 기법이 자연스럽게 자리 잡았습니다.

첫 번째는 “컴포넌트 X를 공유 웹 코드로 옮겨줘”라고 요청하면 프로덕션에 올릴 수 있는 PR을 만들도록 지원하는 스킬과 에이전트 지식 묶음이었습니다. 같은 작업을 수십, 수백 번 반복할 예정이라면 코드를 복사해 붙여 넣는 대신 재사용 가능한 코드로 추출하듯 프롬프트에서 공통으로 재사용할 부분을 뽑아내는 편이 좋습니다. 이렇게 하면 사람에게 작업을 넘기는 과정도 훨씬 단순해집니다. 동료에게 “에이전트에게 이 컴포넌트를 마이그레이션해 달라고 해. 방법은 이미 알고 있어”라고 말했는데 실제로 작동한 처음 몇 번은 마법처럼 느껴졌습니다. 사람에게 개요만 전달해도 에이전트가 필요한 세부 사항을 채우니 대규모 팀 작업을 조율하는 시간을 크게 줄일 수 있습니다. 몇 달 만에 바탕이 되는 웹 프레임워크를 교체하는 동안 개발팀은 계속 커지며 자기 일을 했고, 사람들은 거의 눈치채지 못했습니다. 정말 놀라웠습니다.

두 번째로 유용했던 개선은 에이전트 기반 계획의 추상화 수준을 높인 것입니다. 처음에는 제가 낮은 수준의 목표를 설정하고 추적하고, 에이전트가 계획과 구현을 맡았습니다. 예를 들어 TanStack Start에서 프로젝트 목록을 완전히 표시할 수 있도록 React 컨텍스트 Provider 21개를 찾아 모두 공유 코드로 옮기기로 했습니다. 각 Provider를 별도의 Linear 티켓으로 추적했습니다. Provider를 옮기던 중 각각에 필요한 흥미로운 의사결정이 거의 없다는 점을 깨달았습니다. 충분히 괜찮은 위임 방법만 찾으면 지루한 작업은 모두 AI에 맡겨야 했습니다. 위임 방식은 구현이 아니라 계획을 대상으로 한 단계 위에서 `/goal` 반복을 적용하는 것과 비슷했습니다.

1. 측정 가능한 마이그레이션 지표를 정의합니다. 예를 들어 “Next.js UI를 사용하는 에이전트 도구는 몇 개인가?”를 정하고, 결정론적으로 측정하는 스크립트를 작성합니다.
2. 계획 에이전트에 그 지표를 전달해 마이그레이션 작업을 충분한 크기의 묶음으로 나누게 합니다. “위 내용을 바탕으로 PR 스택으로 구현할 수 있는 일관된 하위 작업을 찾아줘. PR은 최대 12개, PR당 800~1,600줄을 적정 크기로 해줘.” 그렇게 만든 묶음을 구현 에이전트에 넘깁니다. 전체 과정은 [에이전트 코딩 규모 확장에 관한 글](https://lovable.dev/blog/85000-in-tokens-later-scaling-agentic-coding-at-lovable)에서 더 자세히 설명했습니다.
3. 지표가 0이 되거나 해결하기 어려운 장애물이 나올 때까지 반복합니다. 전체 마이그레이션을 완료하는 데 도움이 될 다음 지표를 찾아 같은 과정을 진행합니다.

세 번째로 유용했던 발견은 이식할 수 없는 새 코드 패턴을 찾아 작성자에게 대안적인 리팩터링 방법을 알려주는, 마이그레이션 전용 리뷰 자동화였습니다. 병합된 모든 PR을 에이전트가 분석해 호환성 요구 사항을 충족하는지 확인했습니다. 마찰을 줄이기 위해 기존 기능의 작은 수정은 제외했습니다. 호환되지 않는 새 기능이나 큰 변경 사항이 있으면 작성자에게 알림을 보냈습니다. 해결 방법은 늘 같았습니다. “에이전트에게 호환되게 바꿔 달라고 해. 방법은 이미 알고 있어.” 이런 방식으로 모두가 웹 코드를 호환되게 만드는 방법을 필요한 시점에 필요한 만큼 배웠습니다. 자동화 덕분에 마이그레이션 막바지에 “아차, 이건 아직 옮기지 않았네” 하는 일이 이례적으로 적었습니다.

결국 에이전트는 코드를 옮기고 정확성을 확인하는 일을 충분히 잘 해냈습니다. 에이전트가 수행한 탐색적 테스트, 제가 직접 실행한 스모크 테스트, 단계적 배포를 통해 코드 오너를 전혀 참여시키지 않아도 된다는 확신을 얻었습니다. 2년 전이라면 여러 팀의 협력이 필요했을 일이 개발자 한 명과 에이전트 무리만으로 끝났습니다. 마이그레이션 결과는 대개 스모크 테스트를 통과했고, 몇 차례 작은 수정만 필요했습니다. 이제 TanStack Start 버전의 lovable.dev로 실제 사용자 요청을 처리해도 될 정도였습니다.

## 트래픽 전환

라우트 그룹을 한 번에 하나씩 전환했습니다. 각 라우트 그룹은 여러 단계의 A/B 배포를 거쳤습니다. 제한된 내부 테스트에서 시작해 전사 내부 테스트를 거친 다음, 사용자 1%에게 적용하고 점차 100%까지 확대했습니다. 우리처럼 크고 통합된 시스템은 모든 동작을 분석만으로 예측하는 일이 사실상 불가능합니다. 따라서 주요 품질 관리 수단은 빠른 피드백 주기, 신속한 롤백 능력, 빠르게 문제를 수정할 수 있는 능력입니다. 첫 몇 개 라우트 그룹은 마이그레이션 후 문제를 찾아 수정하느라 내부 테스트에 최대 일주일이 걸렸습니다. 외부 사용자 대상 배포도 비슷한 시간이 필요했습니다. 문제는 더 적었지만, 다음 단계로 넘어가기 전에 소수 사용자 대상 배포에서 제대로 된 신호를 얻으려고 더 오래 지켜봤습니다.

여러 배포를 동시에 진행하면 혼란스러울 수 있어, 외부 사용자를 대상으로 1%에서 100%까지 확대하는 배포는 한 번에 하나만 진행했습니다. 내부 결과가 다음 배포를 시작할 준비가 됐다고 보여도 순서를 기다리게 했습니다. 시스템의 다른 부분을 마이그레이션하는 작업은 계속 병행하고 있었기 때문에 배포를 서두를 이유가 없었습니다. 마지막 몇 개 그룹은 처음부터 끝까지 약 일주일이 걸렸고, 좋은 의미로 별다른 일이 없었습니다.

![각 라우트 그룹이 내부 단계적 배포를 거친 뒤 사용자 1%에서 100%까지 외부 배포를 진행하는 시간표. 그룹마다 1~3주가 걸리고 전체 기간은 두 달입니다.](https://assets.lovable.dev/content/news/nextjs-migration/figma-2026-10-02/rollout-sequence.svg)

*외부 배포는 한 번에 하나씩 진행하고 라우트 그룹마다 시차를 두었습니다. 전체에는 두 달이 걸렸습니다.*

배포 로그를 볼 때 가장 눈에 띄는 실패 양상은 크래시와 기능 버그입니다. 덜 눈에 띄지만 그만큼 중요한 문제가 시스템 성능입니다. 서버 응답 시간, 서버 오류율, 웹 바이탈을 모니터링하고 각 지표에서 두 프레임워크가 어떻게 다른지 추적했습니다. 사용자 다수에게 영향을 주기 전에 성능 문제 대부분을 찾아 해결할 수 있었습니다. 전부는 아니었습니다. 다시 한다면 성능 모니터링에 더 많은 시간을 들이고, 지표상 느려 보이는 변경 사항은 더 적극적으로 롤백하겠습니다.

성능 최적화에서 얻은 교훈 하나는 합성 지표와 실제 사용자 지표를 모두 살펴봐야 한다는 것입니다. 합성 지표는 변동이 적고 에이전트 반복 작업에 쉽게 통합할 수 있어 최적화하기 쉽습니다. 실제 사용자 지표는 최종 목표입니다. 변화가 느리고 직접 영향을 주기도 어렵지만, 사용자가 경험하는 시스템의 실제 상태를 반영합니다.

전체 배포는 약 두 달이 걸렸습니다. 대부분의 기간에는 코드 마이그레이션도 계속 진행했습니다. 마이그레이션을 멈추고 배포에만 집중한 기간은 마지막 2~3주뿐이었습니다. 위험과 시간 사이에는 분명한 절충이 필요합니다. 대체로 우리는 비교적 신중하게 배포했고 그 선택에 만족합니다. 대체로 그렇습니다. 한 번은 상황이 크게 잘못됐습니다.

### 메모리 부족 장애

가장 큰 라우트 그룹의 배포를 막 마쳤을 때였습니다. 순조롭게 진행된 탓에 지나치게 낙관했습니다. 다음 라우트 그룹은 대시보드였습니다. 코드도 적고 위험도 낮았지만 로그인한 모든 사용자의 여정에 포함됐습니다. 내부 배포는 별일 없이 끝났고 공개 배포 비율을 천천히 올리기 시작했습니다. 1%, 5%. 금요일 점심 전에는 20%로 설정했습니다. 오후가 되자 성능에 대한 불만이 들어오기 시작했습니다. 그러다 오류율이 오르기 시작했습니다. 처음에는 서서히, 그다음에는 급격히 올라갔습니다. 오류율은 먼저 0.1%에서 0.5%로 올랐습니다. 그리고 몇 분 만에 약 50%까지 치솟았고 모든 경보가 울렸습니다.

장애는 11분 동안 이어졌습니다. 흔히 그렇듯 문제를 일으킨 커밋을 롤백하는 일은 원인을 파악하는 것보다 훨씬 빨랐고 쉬웠습니다. 알고 보니 런타임 환경의 메모리 한도에 너무 가까이 다가간 상태였습니다. 공개 웹사이트용 정적 데이터 JSON을 마이그레이션한 일이 한도를 넘게 만들었습니다. 전혀 관련 없는 기능이었고 꺼진 플래그 뒤에 숨겨져 있었습니다. 몇 MB가 추가된 것이 마지막 한 방이 됐습니다. 대시보드 배포 비율을 높인 일이 근본 원인은 아니었습니다. 다만 가장 좋지 않은 시점에 더 많은 사용자가 문제를 겪게 했습니다.

왜 문제가 생겼을까요? V8 아이솔레이트는 여러 차례 재사용해야 합니다. 하지만 우리 아이솔레이트는 메모리 한도를 넘겨 종료되기 전까지 평균 10건도 안 되는 요청만 처리했습니다. 비교하자면 현재 기준으로는 배포 빈도에 주로 영향을 받으며 아이솔레이트 하나가 요청 500~1만 건을 처리합니다. 아이솔레이트가 종료되면 그 시점에 처리 중이던 모든 요청에서 오류가 발생합니다.

무엇을 잘못했을까요? 초기 메모리 사용량을 측정하지 않았습니다. 초기 경고를 무시했고 오류율 0.1%를 마이그레이션이 끝나면 살펴볼 문제라고 여겼습니다. 다시 말해 실제 데이터를 충분히 살펴보지 않은 채 지나치게 낙관했습니다.

문제가 무엇인지 명확해지고 나니 장기적인 해결책은 AI를 더 활용하는 일이었습니다. “서버 요청에서 메모리 사용량을 측정하는 방법은 이렇습니다. 사용량을 줄일 아이디어 열 가지를 내고, 프로토타입을 만들어 측정하세요. 좋은 방법은 각각 PR로 적용하세요.” 유망한 아이디어를 가려낼 시간과 토큰, 엔지니어링 감각만 있으면 됩니다. 최근에는 평소 하루 기준으로 메모리 부족 오류가 발생하지 않습니다.

도움이 됐던 메모리 개선 방법은 다음과 같습니다.

- 모듈 수준에서 정적 콘텐츠가 든 수 MB짜리 JSON을 파싱하지 않습니다. 이렇게 만든 객체는 서버 메모리에 계속 남습니다. 원시 문자열로 가져온 다음 요청 핸들러에서 파싱하자 라우트에 따라 메모리 사용량이 2~12배 줄었습니다.
- 목록 API에서 사용하지 않는 필드를 제외해 템플릿에서 몇 MB를 절약했습니다. 템플릿은 수백 개나 되며 카탈로그 페이지에서는 전체 설명이 필요하지 않았습니다.
- 클라이언트 전용 코드를 서버 번들에서 빈 스텁으로 대체했습니다. lovable.dev의 일부는 사실상 브라우저 안의 IDE라서 서버에서는 대부분의 코드가 필요하지 않았습니다. 타입스크립트 컴파일러, Prettier, 구문 강조 도구 등 비슷한 구성 요소를 제외하자 서버 번들 크기가 약 9MB 줄었고, 워커 메모리는 18MB 절약됐습니다. 번들 바이트는 메모리에서 대략 두 배가 됩니다. V8은 문자열에 라틴-1 범위를 벗어난 문자가 하나라도 들어가면 문자열 전체를 2바이트 형식으로 저장하기 때문입니다. 번들 전체는 하나의 문자열로 로드되고, 로케일 데이터에는 국제 문자가 들어 있으므로 이 문자열도 반드시 국제 문자를 포함합니다. 전체 메모리 한도가 128MB라면 이런 차이도 무시할 수 없습니다.

## TanStack Start와 Next.js 비교

수년간 Next.js를 사용한 뒤 제 역대 최대 규모의 프로젝트를 Next.js에서 마이그레이션하며 느낀 점입니다.

### 더 나은 로컬 개발 경험

TanStack Start는 Vite 개발 서버를 사용합니다. Next.js보다 빠르게 시작하고 메모리도 몇 배 적게 사용합니다. 우리 코드베이스에서는 TanStack Start가 10초 만에 시작하며 RAM 1.5GB를 사용하는 반면, Next.js는 시작에 70초가 걸리고 RAM 8GB를 사용합니다. 다른 주요 작업은 실행하지 않은 MacBook M4 Max에서 측정한 수치입니다. 답답함을 호소하는 동료 중에는 Next.js가 RAM을 20GB 넘게 쓰는 경우도 있었습니다. 백엔드 서비스를 디버깅하려는데 로컬 프런트엔드는 별로 필요하지 않은 상황이라면 반가운 결과가 아닙니다.

최신 하드웨어에서도 RAM은 늘 부족합니다. 메모리를 적게 쓰면 숨통이 트입니다. 한 시간에 여러 번 브랜치를 바꾼다면 시작 시간도 더 중요해집니다.

이 수치는 Turbopack을 활성화한 Next.js v16.2 기준입니다. 새 버전인 v16.3에서는 개발 서버 메모리 사용량을 최대 [90% 줄였다고](https://nextjs.org/blog/next-16-3#less-memory-usage-in-dev) 합니다.

### 여전히 헷갈리는 Next.js의 추상화

Next.js는 서버와 클라이언트 간 동형 실행의 복잡한 문제를 다룬 첫 인기 프레임워크였습니다. 현재 상태에 도달하기까지 몇 차례 반복이 필요했던 것도 당연합니다. 저를 포함해 많은 개발자가 서버 컴포넌트, 서버 액션, 레이아웃과 페이지의 분리 때문에 헷갈리는 모습을 봤습니다. 제 실력 문제일지도 모르지만, 정말 불편합니다.

TanStack Start는 업계가 쌓아온 경험을 바탕으로 더 적은 추상화를 도입해 제가 이해하기 쉽습니다. TanStack의 서버 함수, 라우트 로더, 중첩 라우트는 비슷한 혼란을 일으키지 않습니다. 더 직관적으로 느껴집니다.

### TanStack Start에서 에이전트의 성능이 더 좋습니다

까다로운 Next.js 문제를 다룰 때 에이전트가 오래되고 잘못된 조언을 하는 모습을 본 적이 있습니다. 예를 들어 앱 라우터에서 페이지 라우터 API를 사용하려 하거나, v14의 캐시 기본값이 v16에서도 적용된다고 가정하는 식입니다. 원인은 대개 오래된 인터넷 지식이거나 당시 사용 중이던 Next.js 버전에서 올바른 해결책이 무엇인지 에이전트가 놓친 데 있었습니다. Next.js v12, v14, v16이 서로 상당히 다르다는 점은 에이전트에 도움이 되지 않습니다. 학습 자료 상당수는 프레임워크 버전이나 페이지 라우터와 앱 라우터를 명확히 구분하지 않습니다.

TanStack Start는 새로운 프레임워크라 이런 문제가 없다고 생각합니다. 에이전트는 대체로 첫 시도에 올바르게 처리합니다. 제가 보는 실수는 프레임워크를 잘못 이해해서 생긴 것이 아닙니다. 제 생각에 에이전트에게는 서로 모순되는 내용이 많은 대규모 학습 자료보다 작더라도 일관된 학습 자료가 더 낫습니다. 에이전트는 문서와 주변 코드를 읽어 부족한 지식을 채울 수 있지만, 자신 있게 굳어진 잘못된 습관을 쉽게 버리지는 못합니다.

### 대규모 TanStack Start 앱에는 많은 번들러 설정이 필요할 수 있습니다

Next.js에서는 최적의 코드 번들링이 거의 해결된 문제처럼 느껴집니다. 프로덕션 빌드는 대체로 별다른 설정 없이도 효율적입니다. 제가 주로 사용한 최적화 방법은 의존성을 제거하고 `next/dynamic`으로 번들 분할 지점을 추가하는 일이었습니다.

반면 TanStack Start에서 좋은 결과를 내려면 저수준 설정을 꽤 많이 해야 했습니다. 에이전트는 이런 유형의 최적화를 잘 이해하지만, 먼저 필요성을 파악하고 작업을 맡겨야 합니다. 현재 lovable.dev의 빌드 설정에는 사용자 지정 빌드 플러그인이 17개 있습니다. 사용자 지정 코드 분할, 여러 사용자 지정 개발 환경 지원, 에셋 파이프라인 등을 처리합니다. 환경에 따라 다르겠지만 우리 규모의 앱을 설정 없이 운영할 수 있다고 기대하지는 마세요.

## 얻은 것

마이그레이션의 가장 큰 이유이자 성과는 개밥먹기였습니다. 그 밖에도 몇 가지를 얻었습니다.

### 성능

사용자에게 제공하는 웹 바이탈 대부분은 이전과 비슷한 수준입니다. 전반적인 응답 시간은 빨라졌습니다. TTFB 중앙값이 49% 줄었습니다. 하지만 긴 꼬리 구간은 느려졌습니다. 처음에는 p90이 최대 두 배까지 느려졌고, 원래 수준으로 되돌리는 데 어느 정도 작업이 필요했습니다. 현재는 마이그레이션 전보다 16% 빨라졌습니다. 클라이언트 측 지표는 크게 달라지지 않았지만, 이제는 최적화하기 더 쉽다고 느낍니다.

우리 쪽에서는 로컬 개발과 CI/CD 빌드 시간이 모두 단축됐습니다. 웹사이트 프로덕션 빌드는 CI 검사 중 가장 오래 걸리는 경우가 많았습니다. 12분 넘게 걸리는 일도 드물지 않았습니다. 이제 6~9분이면 끝납니다. 아직 최적화 작업을 한 번도 진행하지 않았는데도 그렇습니다. 이 섹션을 작성하는 동안에도 2분을 더 줄일 방법을 찾았습니다. 회사에서 하루에 수백 번 배포한다면 매분이 중요합니다.

### AI 지원 도구

혼자서 그 많은 코드를 다루다 보니 AI 코딩을 어느 규모까지 활용할 수 있는지 한계를 넓혀야 했습니다. 동료와 저는 마이그레이션을 위해 만든 스킬과 도구를 지금도 일상 업무에서 사용합니다.

### 자체 편집

lovable.dev와 사용자 앱이 같은 기술 스택을 사용한 덕분에 자체 편집도 더 쉽게 지원할 수 있게 됐습니다. 이제 Lovable로 lovable.dev를 편집하고 변경 사항을 실시간으로 미리 볼 수 있습니다. Lovable의 비개발 직군 직원이 가장 많이 사용하는 셀프서비스 편집 흐름이 됐습니다. 모두가 빌더이며 모두가 Lovable 자체를 개선할 수 있습니다. 개발자도 매일 자체 편집을 사용하지만, 그 이야기는 나중에 별도의 글로 다루겠습니다.

## 다음 단계

Lovable은 TanStack Start 기반 웹 애플리케이션을 기본 기술 스택으로 정해 두었습니다. 하지만 에이전트와 인프라는 이미 훨씬 더 다양한 기술을 지원할 수 있습니다. 개발 환경에서는 샌드박스 VM에서 무엇이든 실행할 수 있습니다. 이 기능을 활용해 누구나 기존 소프트웨어를 가져와 편집할 수 있도록 하고 싶습니다. 머지않아 Next.js 앱 가져오기를 지원하더라도 놀라지 마세요. 이제 막 Next.js에서 옮겨 온 점을 생각하면 아이러니합니다. 하지만 궁극적으로는 Lovable이 어떤 소프트웨어든 편집하도록 돕고 싶습니다.
